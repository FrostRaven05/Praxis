## 凭据及设备状态边界

普通 JSON 必须采用明确字段白名单，不直接遍历整个数据库、配置目录或环境变量。排除 AI 密钥、登录/刷新令牌、同步凭据、系统安全存储材料及部署秘密。用户输入的业务正文按内容导出，不能声称自动识别并清除正文里人为粘贴的秘密。

本地设备身份、认证会话、远端同步游标、重试状态和 `sync_outbox` 不应作为可直接重放的业务数据复制到新工作空间。业务历史与待发送命令需要分开处理；新工作空间的账号绑定和首次同步应使用新的隔离范围。历史中的 owner/device/operation 标识如何保留或映射，必须与 T28 身份规则一起确定，不能沿用原 profile 后宣称已创建新工作空间。

3. 在提交导入前检查版本、字段类型、日期/时区、枚举、唯一身份、规则区间及所有显式和 JSON 内嵌引用；显示每类对象数量和问题。拒绝不支持的未来版本、损坏引用和冲突身份，保持源工作空间不变。
4. 默认创建全新工作空间。若重映射 ID，统一重写父子关系、链接、来源产物、重点数组、视图查询、重复发生项、回收站 payload 和历史引用；不得把只重写外键列当作完整映射。
5. 在事务或可恢复的暂存工作空间中导入，验证完成后才使新工作空间可见。覆盖写入现有库不能替代合并导入；未提供合并功能时应明确禁止该路径。
6. 实际执行一次导出→全新工作空间恢复→重启→逐项核对。比较数量、正文、日期类型/值、时区、历史规则、所有关系及回收站可恢复行为；若 ID 重映射，按映射后的语义比较，而非仅比较总数。
7. 在校验、写入及切换阶段注入失败，证明原工作空间、其账号绑定和待发送操作均未改变；恢复后的首次同步不得把旧 outbox 重放到原工作空间。该步骤需要 T28 所依赖的真实同步环境验收。
