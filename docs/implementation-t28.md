## 重复发生项身份：已有算法及待验证边界

`store/recurrence.rs` 当前使用 UUIDv5：命名空间为 `Uuid::NAMESPACE_URL`，名称字节为 UTF-8 的 `praxis:occurrence:{templateId}:{YYYY-MM-DD}`。本地另有 `(recurrence_template_id,occurrence_key)` 唯一索引。这能约束单库重复，尚无已验证的 Rust、TypeScript、服务端跨语言生成向量，也未证明双端离线最终收敛。

协议必须固定模板 UUID 的字符串规范化、日期格式、字符编码与命名空间字节顺序；明确 owner/workspace 隔离以及恢复到新工作空间时 ID 是否保留。至少加入固定向量：普通日期、闰日、跨年、同模板不同日期、不同模板同日期，以及 UUID 大小写输入规范化。模板时区发生变化时，日期身份如何保持需和 T19 一致。

即使生成相同任务 ID，两台设备可能根据不同规则版本生成不同标题/安排，或分别编辑与取消同一发生项。不能用 `ON CONFLICT DO NOTHING` 代替冲突处理。若迁移旧数据存在随机 ID 或重复逻辑身份，规范化映射必须原子覆盖父子关系、每日安排、执行事实、记录链接、重点引用、回收站引用及待发命令；重放旧 ID 的命令仍须可解析且不能生成幽灵副本。

## 习惯自然键：本地唯一不等于跨端解决冲突

习惯记录的自然键为 `(habit_id,local_date)`。现有本地 upsert 和 expected_version 能阻止单库陈旧写入，但两台离线设备均可认为某日尚无记录。合并时两次 done 应只贡献一次统计，同时保留必要操作历史；done 对 skipped、done 对撤销及不同备注必须按 T26 显示并解决，不能静默按到达顺序覆盖。

规则主键中的整数 version 目前由本机递增。两台设备可产生相同版本号但不同规则，需要由协议解决或采用全局规则身份映射。历史 entry 的 schedule_version、事件 before 快照和生效区间必须保持对应关系；不允许用最新规则重新解释历史完成率。
